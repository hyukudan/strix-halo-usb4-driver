## Scope and evidence

`72d3fcf802c45d00b300f25b848a93c3a2bd7c7e` (7.3-rc5). This is source review,

## Implemented corrections

### Shared RX credit accounting and parameter safety — patch 0002

`tb_dma_init_rx_path()` allocated the first lane hop from the entire usable
budget without subtracting other DMA paths' reservations. Multiple streams or
USB4NET plus USB4STREAM could therefore over-reserve the same adapter. On USB4
credit-allocation ports, subtract existing reservations, reject exhaustion, and
retain balanced release accounting. Legacy ports must not accumulate a counter
that their release path does not decrement.

The locally writable `dma_credits` parameter had no explicit range validation.
The development policy now accepts **1..127**, matching the 7-bit per-hop field;
0 is deliberately no longer accepted as an ambiguous automatic/zero-credit
request. Invalid writes leave the old value intact. READ_ONCE/WRITE_ONCE avoid
unmarked concurrent accesses. Changing this global parameter affects future
allocations, **not already programmed tunnels**; this is not a live link-speed
control. Existing per-router hardware limits still apply. Keep the default 14
until comparative measurements justify another value.

Guard two arithmetic hazards: a control reservation greater than total buffers
must not become an unsigned credit budget, and an insufficient DP budget must
not become a huge `size_t` stream count after negative division.

### MSI-X bank selection — patch 0002

The captured clear routine selected only a TX or RX base, ignoring additional
32-bit register banks for larger interrupt indices. Select bank and bit from
`ring_interrupt_index()` together. Retain the existing posted-write readback
and the auto-clear-host bypass. This is a general correctness fix; without the
actual machine's hop count and allocated rings, it is not evidence that this
caused its observed bandwidth problem.

### Lower GPU submission overhead — patch 0003

Previously each 4 KiB frame caused its own enqueue lock and descriptor doorbell.
Add a GPL-exported internal list enqueue API. A stopped ring leaves the input
list untouched; successful enqueue owns every frame, including software-queued
frames waiting for descriptor space. Initialize frames and account for all
callbacks before publication. Failure cancels only the unaccepted operation,
without discarding hardware-owned callbacks from other operations.

Fill a descriptor batch, publish it with `dma_wmb()`, then ring the doorbell
once. Empty/full rings do not cause spurious writes. All descriptor completion
interrupt flags remain enabled: this patch does not silently trade correctness
for interrupt suppression. In a mocked ring with 512 available slots, batch
submission performs 1 doorbell write versus 512 individual enqueues. This is a
register-operation count, **not a measured throughput speedup**.

GPU userspace wakeups now correspond to an available whole-operation event or
an error, rather than every individual frame. Preserve standby RX ownership,
peer-agreed identity, reservation fences, cancellation accounting and exclusive
open semantics. No unilateral RX restart or implicit geometry change is added.

### Fence / stop lifetime and buildability — patch 0004

The custom fence release used immediate `kfree()`. Use `dma_fence_free()`, whose
pinned implementation defers freeing through RCU; `base` is the first member of
the allocated object. Reservation readers must not observe freed storage.

`tb_ring_stop()` can return early when the NHI is going away. Zero pending
callbacks alone must not certify that an enabled ring is stopped. Refuse that
certification while either ring remains running and keep the existing
quarantine instead of releasing DMA mappings. This is conservative retention,
not a complete recovery implementation for all controller-removal scenarios.

Fix the shared header's nonexistent userspace include path. Correct the stale
UAPI comment: the implemented RX standby path preserves slot offset and payload
frame count. A changed geometry requires coordinated STOP/RELEASE/new import;
it does not drain and rearm RX locally.

## The link reported below 40 Gb/s

The source's XDomain `rx_speed` / `tx_speed` values are **per lane**. For each
direction separately:

| Speed attribute | Lane count | Raw directional link rate |
| --- | ---: | ---: |
| 20.0 Gb/s | 2 | 40 Gb/s |
| 20.0 Gb/s | 1 | 20 Gb/s |
| 10.0 Gb/s | 2 | 20 Gb/s |

Do not add TX and RX together. A 40 Gb/s raw link is not a guarantee of 40 Gb/s
application payload; 40 Gb/s is 5 GB/s before protocol overhead, not 40 GB/s.
The prior source changes did not alter physical lane training. Increasing DMA
credits cannot turn a single negotiated lane into two.

Patch 0002 reports the failed bonding state, error and refreshed speed/width
when negotiation falls back to enumeration. It does not force unsupported
speeds, retrain an active link, or promise that a firmware/cable/PHY issue is
solved. Existing low-UUID bonding diagnostics are retained.

Run this read-only capture on **both hosts**, with the problematic link connected:

```sh
python3 tools/usb4_diagnose.py --logs > usb4-host-A.json
# Run on the other host with a different filename:
python3 tools/usb4_diagnose.py --logs > usb4-host-B.json
```

Logs can require elevated read permissions; lack of permission is reported, not
silently replaced with a diagnosis. Review logs for hostnames before sharing.
The report maps each router/XDomain to its actual PCI controller, includes both
lane counts and rates, loaded-module source versions when available and the
current global credit parameter. Missing attributes remain unknown. Matching
kernel release names alone do not prove identical binaries.

For a real 20 Gb/s negotiation: record both ends, then compare the same cable
and peer on the working and failing ports; compare connector orientations and
cold reconnects after stopping transfers. If the failure follows a cable,
port, peer or orientation, that distinguishes candidates but does not by itself
prove the defective component. Do not write PHY/debugfs registers blindly.

For an already 40 Gb/s link: compare unidirectional and bidirectional traffic,
one link versus all links concurrently, USB4NET versus the DMA-BUF path, and
small versus large operations. Keep firmware/kernel/credits/ring size fixed
within each comparison. Record CPU time, interrupts, throughput and error counts.
Validate receiver data and producer/consumer synchronization, not just TX local
completion. Measure while all relevant GPU/CPU memory traffic is active too.

## Remaining high-risk or performance work

**AMD teardown recovery.** The snapshot removed the upstream global host-interface
reset quirk. Its own comments record peer TX stalls after restarting RX alone.
Restoring a reset on every path close could destroy other active rings. Correct
recovery needs controller-wide ownership/quiescence, coordination with every
consumer and the peer, and unplug/suspend/reconnect tests. This audit deliberately
does not restore a global reset or silently remove E2E flow control.

**Bounded recovery of quarantines.** Safety retention can retain module/device
references and buffers indefinitely. Any reclamation must have actual proof of
controller quiescence; a timer is not such proof. Exercise disconnect with pending
TX/RX, zero pending frames, open FDs, last close and concurrent services.

**Pipeline depth.** There is only one operation per direction and the device mutex
covers reservation waits. Batching reduces per-frame overhead but does not add
multiple outstanding operations, independent window queues or a versioned
multi-operation ABI. Those need measured bottleneck evidence and a lifetime /
locking redesign, not simply raising ring size. Profile IRQ placement/coalescing
and completion/event overhead before introducing additional workers.

**GPU visibility and end-to-end correctness.** Controller fences do not prove
remote application acknowledgment, validated payload, or GPU cache visibility.
Do not label this path qualified zero-copy GPU RDMA until exporter/importer,
cache synchronization and GPU-consumer validation have been exercised. Do not
disable the IOMMU to hide mapping or synchronization failures.

**Property notifications.** The snapshot's notification revert is left intact;
without original failing traces and peer behavior, blindly restoring it could
reintroduce a discovery loop. Treat service discovery/reconnect separately from
physical link bonding.

## Validation status and reproduction

Executed locally: 3 extracted-function / parser tests and 4 reconstruction-tool
tests, all passing. The C credit/ring tests use GCC with UBSan and exercise
bounds, shared-budget exhaustion/release, legacy behavior, empty/full/wrapped
rings, stopped-ring all-or-nothing ownership, bank selection and doorbell counts.
These local source fixtures reproduce reviewed functions, not the complete
kernel. Reconstruction fixtures also verify that nested Git checkouts cannot
silently skip patches, original-hash failures are rejected, output is not
overwritten, and a failed patch cannot publish a partial result.

The CI suite additionally tests the actual shared header and source lifetime
invariants, verifies both reconstruction methods against the complete checkout,
and compiles affected kernel objects with GPU mode on/off. **The initial GitHub
Actions runs failed before executing any job steps; downloadable job logs were
unavailable. The cause was not established. Therefore neither a complete-overlay
CI pass nor a pinned-kernel compilation is claimed here.** Consult the latest
check results; merely committing a workflow does not validate its code.

Run the complete hardware-free suite in a fresh checkout:

```sh
python3 tools/prepare_overlay.py audited-overlay
USB4_SOURCE_TREE="$PWD/audited-overlay" python3 -m unittest discover -s tests -v
```

See BUILD.md for the complete kernel reconstruction and compile procedure. Object
compilation does not substitute for full module linkage/modpost, target config,
Secure Boot signing, boot tests, lockdep/KASAN stress, GPU coherency or sustained
multi-host hardware tests. No module installation/reload, BIOS write or reboot
was performed. Keep a known-good kernel and use a distinct LOCALVERSION for any
experimental build; do not deploy this draft as a proven fix for 40 Gb/s.
